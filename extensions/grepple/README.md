# Grepple workflow for Grip

A Grip extension that favors Grepple through Bash. It does **not** register or override tools. When loaded in a parent session, it downloads the latest published Grepple CLI and installs the skills from that same release before the first prompt. `/grepple-install` refreshes both explicitly and reloads resources.

The independently versioned official package starts at `1.0.0` and supports Grip `>=0.3.0 <0.4.0`. It uses the typed job-factory, workspace-backend and approved-host APIs. Core version synchronization can extend the upper bound for later Grip releases. Tests validate this checkout and the packaged factory; compiled executable smoke tests and source/license approval remain required before publication. See the [official authoring guide](../README.md).

On session start (including reload, new, and resume), it deactivates `read`, `grep`, `edit`, `write`, and `grepple`, ensures `bash` is active, and leaves unrelated active tools untouched. Grip's built-in tools remain registered and can be re-enabled with `/tools`, except that `edit` calls are blocked while this extension is loaded. The job factory applies the same guidance, tool selection and guard to jobs, but never installs, checks updates, prompts for host approval or registers `/grepple-install` in children.

Before each agent run it adds brief Grepple guidance when Bash is active, unless a custom system prompt is in use. If project instructions already include `## Grepple-first repository workflow`, it adds only a short metadata-selector reminder; otherwise it adds the full workflow prompt. Guidance stays under Guidelines, ahead of Skills, Jobs and Grip documentation, with an append fallback for other prompt layouts. Missing/stale coverage or exhaustive audits require an unfiltered pass. Metadata filters do not apply to graph, grit, architecture, or remote queries.

For Bash calls, the extension passes the proposed shell command to `grepple grep-guard` in the **active tool backend**, never the extension host. It checks `~/.local/bin` as well as the backend's PATH. The CLI's shell-aware classifier blocks legacy local-search commands such as `find`, `grep`, `egrep`, `fgrep`, `rg`, `ag`, `ack`, `fd`, `fdfind`, and `locate`, including supported wrappers; the denial uses the CLI's canonical reason. Append `# grep-guard:allow` only for a genuinely exceptional command. A missing/old CLI, timeout, oversized input or invalid response **fails open**; this is a workflow guard, not a security boundary.

## Installation and updates

1. Load from a checkout with `grip -e extensions/grepple/index.ts`. Once published in the official catalog, install with `grip install official:grepple` or use `/extensions`. Installing the package activates this startup behavior when Grip loads it; the package manager itself does not execute a CLI installer.
2. At resource discovery (startup, reload, new, resume and fork), the extension runs the [official Grepple installer](https://github.com/greppleai/grepple/blob/main/install.sh), which resolves the latest GitHub release and downloads/checksum-verifies it into `~/.local/bin`. This includes activation immediately after `/extensions` installation. It does not trust the presence of an existing binary as evidence that it is current. It then invokes that exact executable with `setup grip`, installing version-matched skills rather than arbitrary `main`-branch skills. **Publish the Grepple release containing `setup grip --skills-dir` before publishing this extension update.**
3. Local Grip skills go to `<agentDir>/skills` (normally `~/.grip/agent/skills`, honoring `GRIP_CODING_AGENT_DIR`), passed explicitly with `--skills-dir`. Resource discovery rescans this host-local directory immediately, so new skills are available before the first prompt without restarting. `/grepple-install` requests a resource reload, which performs the same refresh exactly once; `/reload` also refreshes the CLI and skills. Failed refreshes still rediscover existing skills.
4. For a connected, mapped Grip sandbox, installation runs there first (`setup grip` uses the guest's agent directory), then requests **fresh host approval** to install the CLI and matching skills separately into the local Grip agent directory. The exact host command and mapped cwd are displayed. Approval expires after 60 seconds; each command has a separate 600-second execution limit. Denial/failure leaves the sandbox installation in place and retains existing host skills. Unmapped sandboxes, arbitrary remote daemons and sandboxes without an approval UI are refused before either install; no host execution bypass is used.
5. `grip --offline` or `GRIP_OFFLINE=1` skips startup downloads and uses installed skills; explicit `/grepple-install` also refuses offline. Update/network/skill-install failures are nonfatal and reported; previously installed skills are rediscovered. A CLI update can succeed before skill synchronization fails: retry `/grepple-install` after fixing the error. There is no guarantee of being current while offline or after an update failure.

Review the installer before enabling the extension: its script comes from the repository's `main` branch and is executed in each environment. No `sudo`, shell-profile edits or settings/credential rewrites. Grepple's skill synchronizer manages only its catalogued skill names and preserves unrelated skills. The official extension package itself updates through Grip's existing official-extension manager; its policy is separate from these CLI/skill refreshes.

Add `~/.local/bin` to PATH if needed for other shells; the extension's guard already checks it. Verify with `printf '%s' '{"command":"rg needle ."}' | ~/.local/bin/grepple grep-guard` and expect `"blocked":true`.

## Development

Run `node --import tsx --test extensions/grepple/test/*.test.mjs` from the Grip root. From `packages/coding-agent`, run `node ../../node_modules/vitest/dist/cli.js --run test/official-grepple-artifact.test.ts` to check deterministic packaging and isolated standalone-style parent/job factory loading. Tests mock downloads and never run the network installer. Run `npm run check` from the repository root before merging.

Use Bash for `grepple overview`, `grepple tree --depth 1`, focused `grepple --at` reads and `grepple write --root .` with a quoted literal heredoc. The directives are `::grepple replace PATH START [END]`, `::grepple create PATH` and `::grepple delete PATH SHA256`. The next directive or EOF ends its body; there is no end marker or `::grepple end`. Obtain clean Grepple anchors before replacement and the current SHA-256 before deletion. Bash runs in the active workspace backend; separately approved installation is the only host-side action.
